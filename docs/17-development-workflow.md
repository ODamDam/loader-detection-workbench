# 개발 운영 워크플로

## 1. 목적과 문서 경계

이 문서는 저장소 작업의 접수, 분류, 계획 승인, 구현, 검증, 보고 및 중단
절차를 정의한다. 프로젝트 목표나 아키텍처를 새로 결정하지 않고 기준 문서와
현재 `PLANS.md`를 실제 작업에 적용한다.

`AGENTS.md`는 항상 적용되는 비협상 규칙을, `PLANS.md`는 활성 마일스톤의
범위와 상태를 관리한다. 역할과 안전 규칙의 요약은 두 문서를 참조하며,
여기에서는 작업자가 따라야 할 상세 절차와 기록 형식을 설명한다.

## 2. 작업 접수와 조사

작업을 시작할 때 가능한 범위에서 다음을 확인한다.

- 사용자가 원하는 관찰 가능한 결과
- 관련 Issue 또는 하나의 명확한 작업 단위
- 관련 요구사항, ADR과 활성 마일스톤
- 포함 범위와 제외 범위
- 예상 변경 파일
- 공개 인터페이스 또는 지속 데이터 영향
- 완료 조건과 검증 방법
- 보안, 데이터, 네트워크와 외부 시스템 영향
- 별도 승인이 필요한 동작

명시적인 구현 요청이 없으면 읽기 전용 조사와 계획까지만 수행한다. 조사 중
문서 충돌이나 미결 결정을 발견하면 관련 문서, 구현 영향, 선택지와 권장안을
보고하고 임의로 결정하지 않는다.

## 3. 작업 분류

### 3.1 조사·설명 작업

문서·코드 조사, 설계 검토, 상태 보고와 원인 진단이다. 외부 상태 변경이나
파일 수정을 포함하지 않는다.

### 3.2 단순 구현 작업

다음 조건을 모두 충족하는 변경이다.

- 목표와 완료 조건이 명확하다.
- 변경이 소수 파일에 국한된다.
- 아키텍처, 데이터 모델 또는 보안 경계를 변경하지 않는다.
- production 또는 build dependency를 추가하지 않는다.
- DB나 공개 인터페이스의 호환성을 깨지 않는다.
- 위험 분석 실행을 포함하지 않는다.

사용자가 구현을 명시적으로 요청한 단순 작업은 범위와 짧은 계획을 알린 뒤
진행할 수 있다.

### 3.3 비단순 구현 작업

다음 중 하나라도 해당하면 구현 계획을 먼저 제출하고 승인받는다.

- 여러 모듈 또는 계층을 변경한다.
- 새로운 사용자 흐름을 구현한다.
- DB 스키마나 지속 파일 형식을 변경한다.
- CLI, Case Bundle 또는 공개 인터페이스를 변경한다.
- production 또는 build dependency를 추가한다.
- VirtualBox 등 Hypervisor, Guest Orchestrator, AI Provider 또는 네트워크를 다룬다.
- 보안 경계나 공개 범위를 변경한다.
- 완료 조건 또는 구현 방식이 모호하다.

### 3.4 위험 분석 실행

다음 동작은 일반 개발 명령과 구분하며, 계획 승인과 별도로 실행 직전에
명시적 승인을 받는다.

- 실제 Hypervisor 명령과 VM 시작·종료·스냅숏 복원
- Guest Orchestrator 실행
- 실제 샘플, simulator 또는 분석 대상 프로세스 실행
- 분석 VM 외부 네트워크 활성화
- 실제 샘플 경로 접근
- 샘플 또는 민감 로그의 외부 전송

Python 실행, 테스트, lint, format, type check, 패키징 검사 등 일반 개발
명령은 승인된 구현 작업의 검증 범위에 포함한다. 일반 개발 명령이 분석
대상을 실행하거나 외부 전송을 유발한다면 위험 분석 실행으로 다시 분류한다.

## 4. 구현 계획

비단순 작업 계획에는 다음을 포함한다.

### 목표

사용자에게 제공할 결과를 설명한다.

### 포함 범위와 제외 범위

이번 작업에서 변경할 항목과 후속 작업으로 남길 항목을 구분한다.

### 관련 기준선

요구사항 ID, ADR, 마일스톤, 백로그 또는 Issue를 연결한다.

### 변경 예정 파일

생성, 수정 및 삭제할 파일을 가능한 범위에서 구분한다.

### 완료 조건과 검증

관찰 가능하고 테스트할 수 있는 완료 조건, 실행할 검사, fixture 또는 mock
전략을 제시한다.

### 위험과 승인 지점

Dependency, 공개 인터페이스, 민감 데이터, VM, 네트워크, 외부 Provider와
Git 영향을 설명한다.

## 5. 승인과 범위 변경

사용자의 승인은 제출한 목표, 범위, 변경 예정 파일과 완료 조건에 적용된다.
구현 중 다음 사항이 발견되면 범위를 자동 확장하지 않고 다시 보고한다.

- 새로운 production 또는 build dependency가 필요함
- 승인되지 않은 아키텍처 결정이 필요함
- DB 또는 공개 인터페이스의 breaking change가 필요함
- 예상하지 않은 민감 데이터 또는 restricted artifact가 발견됨
- 위험 분석 실행 또는 외부 전송이 필요함
- 기존 사용자 변경과 충돌함
- 완료 조건을 변경해야 함
- 관련 없는 결함이나 리팩터링 기회가 발견됨

승인된 설계 경계 안의 작은 내부 세부사항은 합리적으로 결정할 수 있다.
사용자 결과, 호환성 또는 안전 경계를 바꾸는 결정은 별도 승인을 받는다.

## 6. 구현 원칙

- 승인된 범위만 변경한다.
- 관련 없는 파일을 정리하거나 재포맷하지 않는다.
- 기존 사용자 변경을 보존한다.
- 실패를 성공 상태로 변환하지 않는다.
- 부분 산출물과 오류 원인을 가능한 범위에서 보존한다.
- 관찰 가능한 동작 변경에는 테스트와 사용자 문서를 함께 갱신한다.
- 구현은 `AGENTS.md`의 아키텍처와 데이터 경계를 따른다.

## 7. 의존성 도입 절차

새 production 또는 build dependency가 필요하면 도입 전에 다음을 제시하고
사용자 승인을 받는다.

- 도입 목적과 필요한 기능
- 표준 라이브러리 또는 기존 dependency 대안
- production, build 또는 development 분류
- 버전 정책과 lockfile 영향
- 유지보수 상태와 라이선스
- 보안·공급망 및 Windows 패키징 영향
- 향후 제거 또는 교체 가능성

Development dependency도 목적과 범위를 계획에 기록하며 관련 없는 도구를
함께 추가하지 않는다. 설치 또는 lockfile 갱신은 승인된 구현 범위에서만
수행한다.

## 8. 데이터와 공개 인터페이스 변경

다음 항목은 지속 또는 공개 인터페이스로 취급한다.

- SQLite 스키마와 migration
- Project, Case, Artifact 및 Rule ID
- 상태 값과 상태 전이
- Case Bundle과 manifest
- 정규화 이벤트 스키마
- CLI 명령, 인자, 출력과 exit code
- 보고서와 Publication Bundle 형식
- Provider, Adapter 및 Execution Profile 인터페이스

변경 전 기존 데이터와 사용자 흐름에 미치는 영향, 하위 호환성, versioning
또는 migration, rollback, 오류 처리, 테스트 전략과 문서·ADR 변경 여부를
설명한다. Breaking change는 사용자 승인 없이 구현하지 않는다.

## 9. 테스트와 품질 검사

구체적인 도구와 명령은 활성 `PLANS.md`의 승인된 결정을 따른다. 변경에
적용 가능한 다음 검사를 수행한다.

- 단위 및 관련 통합 테스트
- CLI 또는 사용자 흐름 smoke test
- lint와 format check
- strict type check
- 문서와 도움말 일치 여부
- 민감정보와 금지 자료 포함 여부
- 최종 변경 범위

테스트는 정상 경로뿐 아니라 오류와 부분 실패 경로를 검증한다. 실제 악성
샘플 대신 sanitized, harmless fixture를 사용하고 실제 Hypervisor 호출보다
mock, dry-run, fixture와 command builder 검증을 우선한다. 외부 네트워크에
의존하지 않으며 시간, UUID와 임시 경로 같은 비결정적 요소를 분리한다.
Windows의 Unicode, 공백과 긴 경로도 고려한다.

검사를 실행하지 못하면 명령, 사유, 영향받는 완료 조건, 재현 방법과 대체
검증 여부를 기록한다. 필수 검증을 완료하지 못한 작업이나 마일스톤은
`verification_blocked`로 처리하며 완료로 보고하지 않는다.

## 10. Definition of Done 적용

`docs/13-definition-of-done.md`의 조건 중 현재 작업에 적용 가능한 항목만
평가한다. 예를 들어 SQLite를 도입하지 않는 저장소 부트스트랩에는 SQLite
저장 조건을 적용하지 않는다.

작업은 다음 조건을 충족해야 완료이다.

- 승인된 요구사항 또는 Issue 완료 조건을 충족한다.
- 적용 가능한 테스트와 품질 검사가 통과한다.
- 관련 오류와 부분 실패 경로가 처리된다.
- 사용자 문서 또는 CLI 도움말이 구현과 일치한다.
- 민감정보와 금지 자료가 포함되지 않는다.
- 필요한 ADR과 결정 등록부가 갱신된다.
- 최종 자체 검토를 완료한다.
- 미실행 필수 검증이 없다.

## 11. 안전·외부 전송·공개 절차

악성코드와 VM 안전 통제는 `AGENTS.md`, `docs/11-security-and-safety.md`와
관련 ADR을 적용한다. 위험 실행 전에는 대상, 해시, VM, snapshot, 네트워크
모드, 명령, 수집 범위, timeout과 복원 정책을 사용자에게 제시한다.

게스트 해시 불일치, 외부 라우팅 가능성 또는 준비 상태 검사 실패 시 실행하지
않는다. 실행 후 Clean Snapshot으로 복원하며 복원 실패 시 다음 실행을
차단한다.

외부 AI Provider를 사용하려면 Provider, 허용·제외 필드, 비식별화, 보존
정책과 실패 시 대체 경로를 사전에 승인받는다. AI 출력은 제안으로 취급하고
룰의 최종 채택은 사용자가 승인한다.

Publication Bundle은 금지 자료, 개인정보, 인증정보, 로컬 절대 경로와
재배포 권한을 검사하고 manifest를 확인한 뒤 사용자 승인을 받아 공개한다.

## 12. Git과 원격 작업

Git과 원격 상태를 변경하는 작업은 사용자의 명시적 승인 범위에서만 수행한다.
다음 작업은 각각 승인 대상이다.

- `git add`와 commit
- push와 merge
- tag와 release
- branch 삭제와 이력 변경
- GitHub repository 생성
- Issues, Milestones와 Project Board 변경

사용자가 Git 명령을 금지하면 읽기 전용 Git 명령도 실행하지 않는다. Git
작업을 승인받은 경우에도 변경 범위, 포함 파일, 검증 결과, 민감정보와 관련
없는 사용자 변경을 먼저 확인한다.

## 13. 최종 자체 검토

구현과 검증 후 다음을 확인한다.

- 승인된 목표와 완료 조건을 충족했는가
- 승인 범위 밖 변경이나 관련 없는 리팩터링이 있는가
- 정상·오류·부분 실패 경로가 처리되는가
- 아키텍처와 런타임 데이터 경계를 지켰는가
- secret, 개인정보, 로컬 절대 경로나 restricted artifact가 포함되었는가
- 문서, CLI 도움말과 구현이 일치하는가
- ADR 또는 결정 등록부 갱신이 필요한가
- 실행한 검증과 미실행 검증이 정확히 기록되었는가
- 잔여 위험과 제한사항이 기록되었는가

승인된 범위 안의 문제는 수정하고 관련 검증을 다시 수행한다. 범위 확장이
필요한 문제는 별도 후속 작업으로 보고한다.

## 14. 중단 및 차단 기준

다음 상황에서는 안전한 조사까지만 수행하고 구현 또는 실행을 중단한다.

- source of truth 문서가 충돌함
- 사용자 승인이 필요한 결정이나 범위 확장이 필요함
- 미승인 dependency 또는 breaking change가 필요함
- 실제 샘플 접근, 위험 실행, 외부 네트워크 또는 외부 전송이 필요함
- VM 준비, 네트워크 격리 또는 해시 검사가 실패함
- 스냅숏 복원에 실패함
- restricted artifact 또는 secret이 발견됨
- 기존 사용자 변경과 안전하게 병합할 수 없음
- 필수 검증을 실행할 수 없음

중단 보고에는 중단 지점, 완료된 부분, 원인, 안전·데이터 영향, 필요한 사용자
결정과 가능한 후속 조치를 포함한다.

## 15. 완료 보고 템플릿

### 작업 요약

구현한 결과와 사용자에게 제공되는 동작을 설명한다.

### 변경 파일

생성, 수정 및 삭제 파일을 구분한다.

### 구현 내용

핵심 설계, 사용자 흐름과 오류 처리를 설명한다.

### 실행한 검증

실제로 실행한 명령과 결과를 기록한다.

### 완료 조건

각 완료 조건의 충족 여부를 확인한다.

### 미실행 검증

명령, 실행하지 못한 이유, 영향과 사용자가 재현할 방법을 기록한다.

### 보안 검토

샘플, 민감정보, VM, 네트워크, 외부 Provider, 공개 범위와 금지 자료 영향을
보고한다.

### 잔여 위험과 제한사항

알려진 한계, unresolved 결정과 후속 작업을 기록한다.

### Git 작업

승인되어 실제 수행한 Git 또는 원격 작업만 기록한다. 사용자의 요청 없이
commit 또는 원격 작업을 수행하지 않는다.

### 권장 commit 메시지

필요하면 Conventional Commit 형식의 메시지를 제안한다. 별도 승인 없이
직접 commit하지 않는다.
